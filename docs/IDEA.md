# AI Support Agent для мульти-тенант платформи бронювань

PolyTech Code Fest · трек "AI Customer Support Automation" · 2026-10-31
Статус: концепт для обговорення з ментором (робоча назва, ще не затверджена).

## 1. Проблема

- Чат-боти підтримки **пояснюють, але не діють**: клієнт отримує текст, а дію все одно робить людина.
- При передачі людині **губиться контекст**: клієнт переказує все заново.
- Дії від імені бізнесу (refund, перенесення, виняток) **небезпечні без моделі дозволів**, тому
  бізнеси бояться давати AI права.
- Бізнеси з однаковим продуктом мають **різні правила** (політика скасування, винятки, передоплати),
  і жорстка автоматизація їх не покриває.

## 2. Продукт-сцена (будує тіммейт)

Мульти-тенант платформа онлайн-бронювань (у стилі Fresha / Calendly):

- **B2B тенанти:** салони, клініки, студії. У кожного свій розклад, майстри, послуги, передоплати,
  власна політика скасування та дозволи для агента.
- **B2C користувачі:** клієнти тенантів, які бронюють, переносять, скасовують, платять.

Продукт навмисно простий. Уся новизна в агенті.

## 3. Агент (будуємо ми)

AI-агент у стилі Cursor, але для support: має **tools на весь продукт** і діє в межах дозволів тенанта.

Що він робить:

1. **Розуміє справжню мету.** "Дитина захворіла, не встигну завтра на 10" — це не "скасувати",
   а "перенести і не втратити гроші".
2. **Міркує над політикою тенанта + контекстом клієнта.** Історія візитів, no-show, правила салону,
   наявність goodwill-винятків.
3. **Діє через tools** (перенести бронь, повернути передоплату, застосувати виняток, зняти/нарахувати
   no-show fee, знайти вільні слоти, написати клієнту).
4. **Staged autonomy.** Кожен tool має рівень ризику. Безпечні дії виконує сам; ризикові показує
   людині як **approval card** із reasoning і кнопкою "Виконати" / "Скасувати". Тенант сам
   налаштовує межі (наприклад: refund до 500 грн автоматично, вище з апрувом).
5. **Інтерактивні відповіді.** Замість стіни тексту агент рендерить HTML-картки: слоти для вибору,
   таймлайн бронювання, підсумок рішення, кнопки дій.
6. **Copilot для support-команди та власника.** Пропозиції дій, пояснення рішень, можливість
   відкотити, тріаж вхідних за терміновістю.
7. **Аналітика.** Логує намір, дії, рішення; зводить метрики: що вирішено автономно, де людина
   відповіла гірше за політику, типові причини звернень.

## 4. Чому це AI, а не автоматизація

Автоматизація: правило "скасування < 24 год → передоплата не повертається" і кнопка в адмінці.
Агент: бере брудне формулювання клієнта, зважує політику, історію і контекст, обирає між кількома
валідними варіантами, пояснює вибір людині і бере відповідальність лише в межах дозволів.
Той самий запит від постійного клієнта і від новачка з двома no-show дає різні дії, і агент показує чому.

## 5. Демо-сценарії

**A. Перенесення з goodwill-винятком (автономно).**
Клієнт пише про хворобу дитини. Агент бачить: 12 візитів, 0 no-show, виняток дозволений. Знаходить
3 слоти, показує картку, переносить, зберігає передоплату. Власнику в copilot: "переніс, виняток
застосував, ось чому" + кнопка відкату.

**B. Той самий запит від ризикового клієнта (з апрувом).**
Новий клієнт, 2 no-show. Агент не робить виняток сам, а показує support-агенту картку: два варіанти,
reasoning, рекомендація. Людина клікає, агент виконує і сам відповідає клієнту.

**C. Тріаж і зведення (ops).** Декілька вхідних одночасно: агент ранжує за терміновістю (запис через
годину > питання про ціни), групує схожі, дає власнику зведення дня.

## 6. Архітектура (high level)

```
[Чат клієнта]      [Copilot support/власника]
       \                 /
        \               /
      [Agent service: LLM loop + tool router + permission engine + card renderer]
                      |
            tools-контракт (MCP або HTTP)
                      |
      [Продукт тіммейта: бронювання, тенанти, клієнти, платежі, політики]
```

- Agent service незалежний від продукту: tools описані контрактом із рівнем ризику. Будь-який продукт,
  що виставить свої операції так само, отримує агента.
- Permission engine: політика тенанта × рівень ризику tool × контекст клієнта → autonomous / needs
  approval / forbidden.
- Card renderer: агент повертає структуровані блоки, UI рендерить їх як інтерактивні HTML-картки.

## 7. Поділ робіт

- Тіммейт: скелет платформи (сутності, API, сід-дані для 2–3 тенантів, базовий UI).
- Ми: agent service, permission-модель, картки, copilot, аналітика. Спочатку скелет агента,
  потім функціонал.

## 8. Відповідність критеріям

| Критерій | Чим закриваємо |
|---|---|
| Operational Impact | дії замість відповідей, тріаж, зведення, менше ручної роботи |
| Innovation | staged autonomy, налаштовувана тенантом; агент як плагін до будь-якого продукту |
| Use of AI | LLM у центрі: намір, reasoning, вибір дій, пояснення |
| Reasoning & Context | політика тенанта × історія клієнта × терміновість, прозоре пояснення |
| Presentation & Demo | два екрани поруч, картки, живий апрув |

## 9. Питання до ментора

1. Чи достатньо MVP із двома екранами (чат клієнта + copilot), чи важливіше показати одну сторону глибше?
2. Який рівень автономності виглядає переконливо для журі: більше автономних дій чи більше апрувів?
3. Чи варто робити tools через MCP (сильніше для "Innovation"), чи простий HTTP-контракт і менше ризику?
4. Чи не затягне мульти-тенант обсяг роботи тіммейта? Мінімум: 2 тенанти з різними політиками.
