# Дизайн: платформа бронювань + MCP (частина продукту)

Дата: 2026-10-31 · Автор частини: власник продукту · Статус: погоджено
Базується на спеці тіммейта «скелет застосунку — мульти-тенант платформа бронювань»
(далі — «спека агента»). Агента і його permission engine робить тіммейт, тут їх немає.

## 1. Навіщо

Хакатон PolyTech Code Fest, кейс «AI Customer Support Automation»: AI має не відповідати, а
виконувати реальні дії. Наша ідея — універсальна AI-підтримка для бізнесів, що працюють за
записом (салони, клініки, студії). Одна платформа, різні правила в кожного бізнесу, і агент на
однакове звернення діє по-різному.

Ця частина:
- повноцінний продукт: бізнес керує всім через адмінку (CRUD), клієнти записуються на сайті;
- сторінка підтримки (чат), до якої тіммейт підключить свого агента;
- HTTP JSON API, яким користуються сайт і агент;
- MCP-сервер, через який агент отримує дії як інструменти;
- реалістичні мок-дані в PostgreSQL; усе запускається через Docker.

## 2. Цілі, не-цілі, анти-цілі

**Цілі**
- CRUD через UI і API для: бізнесів (тенантів) і їхньої політики, майстрів і їхнього графіка,
  послуг, клієнтів, бронювань.
- Дії підтримки зі спеки агента (перенести, скасувати, повернути, зняти штраф, виняток,
  повідомлення, тікет) — у формі контракту зі спеки агента.
- Сторінка підтримки для клієнта + інбокс підтримки в адмінці.
- MCP з діями підтримки.
- Мок-дані: демо-клієнти зі спеки агента + «живий» фон (історія бронювань за місяць).
- `docker compose up` піднімає все.

**Не-цілі (окремим кроком, якщо лишиться час)**
- Купівля підписки бізнесом, аналітика/дашборд власника, прогноз no-show, авторизація,
  реальні платежі й SMS.

**Анти-цілі (провал, навіть якщо «працює»)**
- API розходиться з контрактом, який очікує агент тіммейта.
- Демо неможливо повторити: дані не скидаються в початковий стан.
- Апка сама перевіряє політику тенанта щодо дій агента (це робота агента; апка — лише
  цілісність даних).
- Сайт не запускається «з нуля» однією командою на чужій машині.

## 3. Обмеження

- Бекенд: Python 3.14, FastAPI, SQLAlchemy 2, PostgreSQL 16, менеджер пакетів `uv`.
- Фронтенд: Next.js (App Router) + React + TypeScript, Tailwind.
- MCP: Python, FastMCP.
- Docker Compose: `db` (5432), `backend` (8001), `mcp` (8002), `web` (3000).
  Node і Postgres локально не потрібні — усе в контейнерах (тож старий Node 18 не заважає).
- Пріоритет: API + MCP (від них залежить тіммейт) → сторінка підтримки → адмінка CRUD →
  сторінка запису.

## 4. Підходи (розглянуті)

| Варіант | Суть | Компроміс |
|---|---|---|
| A. Усе на Python (FastAPI + Jinja/HTMX + FastMCP) | один проєкт | найшвидше, але простіший сайт |
| B. Усе на TypeScript (Next.js + MCP TS SDK) | одна мова | більше налаштувань |
| **C. FastAPI + FastMCP на бекенді, Next.js/React на фронті** | **обрано** | найкращий сайт, але дві мови |

Обрав власник продукту: бекенд Python FastAPI, фронт React + Next.js, PostgreSQL, Docker.

**MCP поверх HTTP API, а не напряму до бази** (рішення Claude): сайт, MCP і агент ходять через
один API, тож перевірки цілісності в одному місці.

## 5. Що вирішено

### 5.1 Структура репо

Уся частина продукту — у папці `site/` у корені репо; шляхи нижче відносно неї.

```
docker-compose.yml
app/
  backend/     FastAPI: models, schemas, routers, services, seed, tests (pytest)
  mcp/         FastMCP-сервер, тонкий клієнт до API
  web/         Next.js
docs/
  superpowers/specs/ …
  features/<фіча>/   10 файлів документації на фічу (див. 5.9)
```

### 5.2 Модель даних (PostgreSQL)

Поля і значення — як у спеці агента (розділ 3); id — рядки (людські slug у сіді: `lumen`,
`olena`, `b-olena-1`; нові записи — короткі випадкові id). Таблиці:

- `tenants` — id, name, kind, timezone, description, address, phone, instagram (опц.),
  `policy` (JSONB у формі Policy зі спеки агента).
- `staff` — id, tenant_id, name; `staff_services` (зв'язок з послугами).
- `staff_schedule` — staff_id, weekday (0–6), start_time, end_time. Немає рядка = вихідний.
- `services` — id, tenant_id, name, duration_min, price.
- `clients` — id, tenant_id, name, phone (унікальний у межах тенанта), notes.
  `visits_count` і `no_show_count` **рахуються** з бронювань (completed / no_show), у відповіді
  API віддаються як поля, як у спеці.
- `goodwill_exceptions` — id, client_id, booking_id, date, reason.
- `bookings` — id, tenant_id, client_id, staff_id, service_id, start, end, status,
  prepayment_amount, prepayment_status, no_show_fee_amount, no_show_fee_status
  (`charged|waived|none`). В API — вкладені об'єкти `prepayment` і `no_show_fee`.
- `booking_events` — booking_id, ts, event, by, note (= `history` в API).
- `outgoing_messages` — як у спеці агента.
- `tickets` — як у спеці агента.
- `conversations` — id, tenant_id, client_id (nullable, поки клієнт не ідентифікований),
  status (`open|closed`), created_at.
- `chat_messages` — id, conversation_id, role (`client|agent|human`), text, ts.

Схема створюється на старті (`create_all`), без міграцій (рішення Claude: на хакатоні міграції
не окупаються).

### 5.3 API

Префікс `/api`. Помилки — `{"error", "message"}` з кодами `not_found`, `invalid_state`,
`slot_taken`, `validation` (як у спеці агента).

**Контракт агента — без змін форми** (`/api/tenants/{t}/...`): GET тенанта, клієнта (з
бронюваннями), пошук клієнта за телефоном, бронювання (з вкладеними сутностями), слоти; дії
reschedule, cancel, refund, waive-no-show, goodwill, messages, tickets.

**CRUD (для сайту)**

| Ресурс | Ендпоінти |
|---|---|
| Тенанти | `GET/POST /tenants`, `GET/PATCH/DELETE /tenants/{t}`, `PUT /tenants/{t}/policy` |
| Майстри | `GET/POST /tenants/{t}/staff`, `GET/PATCH/DELETE …/staff/{id}`, `PUT …/staff/{id}/schedule` |
| Послуги | `GET/POST /tenants/{t}/services`, `GET/PATCH/DELETE …/services/{id}` |
| Клієнти | `GET/POST /tenants/{t}/clients` (`?phone=`, `?q=`), `PATCH/DELETE …/clients/{id}` |
| Бронювання | `GET /tenants/{t}/bookings?from=&to=&staff_id=&status=`, `POST …/bookings`, `PATCH …/bookings/{id}` (статус completed/no_show, нотатки), `DELETE …/bookings/{id}` |
| Повідомлення, тікети | `GET …/messages?client_id=`, `GET …/tickets?status=`, `PATCH …/tickets/{id}` (закрити) |
| Демо | `POST /api/admin/reset` — очистити і засіяти заново |

Правила цілісності (рішення Claude):
- видалити майстра, послугу чи клієнта з майбутніми `scheduled` бронюваннями — 409
  `invalid_state`; видалення тенанта видаляє все його;
- нове бронювання: клієнт за `client_id` або `{name, phone}` (знаходиться чи створюється);
  якщо `prepayment_required` — передоплата = ціна послуги, `held` (оплата імітується);
  зайнятий слот чи поза графіком майстра — 409 `slot_taken`;
- позначка `no_show` нараховує `no_show_fee` з політики тенанта (`charged`);
- кожна зміна бронювання пише подію в `booking_events` з `by` (`human:admin` з адмінки).

Слоти: старт на сітці 60 хв у графіку майстра, тривалість = `duration_min` послуги; слот
вільний, якщо не перетинається з `scheduled` бронюваннями майстра і не в минулому.

### 5.4 Підтримка (чат) і підключення агента

- `POST /api/tenants/{t}/support/conversations` → нова розмова.
- `POST …/support/conversations/{id}/messages` `{text}` — повідомлення клієнта.
- `GET …/support/conversations/{id}/messages?after=` — нові повідомлення (сторінка опитує).
- `GET …/support/conversations` — список для інбоксу адмінки.
- `POST …/support/conversations/{id}/reply` `{text, role}` — відповідь агента або людини.

Як підключається агент (рішення Claude, узгодити з тіммейтом): якщо задано `AGENT_URL`,
бекенд після повідомлення клієнта шле `POST {AGENT_URL}/chat` з
`{tenant_id, conversation_id, client_id, messages}`; агент відповідає `{reply}` (бекенд
зберігає як `role=agent`) або сам пише через `/reply`. Без `AGENT_URL` — автовідповідь
«Агент підтримки ще не підключений». Повідомлення, які агент шле через `POST /messages` з
`channel=chat`, теж з'являються в останній відкритій розмові цього клієнта.

### 5.5 Сховище і мок-дані

- Сід запускається, якщо база порожня, і по `/api/admin/reset`.
- Час рахується відносно «зараз» у `Europe/Kyiv`, щоб «завтра 10:00» завжди було завтра.
- **Демо-ядро** — рівно як у розділі 5 спеки агента: Lumen Beauty (olena, max, ira) і
  DentaPlus (petro, anna) з їхніми бронюваннями, політиками і лічильниками.
  `b-ira-1`: передоплата 500 `held`; `b-anna-1`: `no_show`, штраф 500 `charged`;
  виняток Ірини 30 днів тому.
- **Фон**: у кожного тенанта 3 майстри, 4–6 послуг, ~25 клієнтів, бронювання за останні
  30 днів (більшість completed, частина cancelled/no_show) і на 7 днів уперед так, щоб
  лишались вільні слоти (агент має знайти ≥3 варіанти). Фон не змінює лічильники
  демо-клієнтів. Генерація детермінована (фіксований seed випадковості).

### 5.6 MCP

- Інструменти: `get_tenant`, `find_client_by_phone`, `get_client`, `get_booking`, `find_slots`,
  `reschedule_booking`, `cancel_booking`, `refund_booking`, `waive_no_show`, `add_goodwill`,
  `send_message`, `create_ticket`. Кожен приймає `tenant_id`, а дії — `by` (за замовчуванням
  `agent`).
- Опис кожного інструмента пояснює, коли його викликати і що він змінює.
- Помилки API повертаються агенту текстом (`slot_taken: …`), без падіння.
- Транспорт: streamable HTTP (контейнер `mcp`, порт 8002) і stdio для локального запуску.
- `APP_API_URL` (у Docker — `http://backend:8001`).

### 5.7 Сайт (Next.js)

Публічна частина:
- `/` — список бізнесів.
- `/b/[tenant]` — сторінка бізнесу (як профіль у Booksy): назва, опис, адреса, контакти,
  майстри, послуги з цінами, правила скасування людською мовою (генеруються з Policy),
  кнопка «Записатись» і кнопка «Підтримка».
- `/b/[tenant]/book` — запис: послуга → майстер (опц.) → слот → ім'я і телефон → підтвердження.
- `/b/[tenant]/support` — чат підтримки: клієнт пише, бачить відповіді агента/людини.
  Режим `?embed=1` — без шапки, для вбудовування.

Бізнесу не потрібен свій сайт: посилання на `/b/[tenant]` ставиться в Instagram, Google Maps.

**Віджет (stretch, після основного):** `GET /widget.js` з атрибутом `data-tenant` малює
плаваючу кнопку чату на чужому сайті й відкриває `/b/[tenant]/support?embed=1` в iframe.
Для демо — статична сторінка «власного сайту салону» з цим віджетом. Агенту все одно, з
якого каналу прийшов клієнт: розмова завжди несе `tenant_id`.

Адмінка `/admin/[tenant]`:
- **Бронювання** — тиждень (таблиця по днях і майстрах), фільтри; картка бронювання з
  таймлайном `history` (подія від `agent` підсвічена), дії: створити, редагувати, позначити
  completed/no_show, скасувати, видалити.
- **Клієнти** — список з пошуком, картка клієнта (бронювання, винятки, лічильники), CRUD.
- **Майстри** — CRUD + графік по днях тижня + послуги майстра.
- **Послуги** — CRUD.
- **Налаштування** — дані бізнесу і політика (усі поля Policy, включно з дозволами агента).
- **Підтримка** — розмови (можна відповісти як людина), тікети (закрити), вихідні повідомлення.
- Кнопка «Скинути демо».

Бронювання і підтримка оновлюються опитуванням API кожні ~3 с, щоб на демо дії агента
з'являлись без перезавантаження. Браузер ходить в API за `NEXT_PUBLIC_API_URL`
(`http://localhost:8001`); CORS відкритий.

### 5.8 Готовність

- `docker compose up` на чистій машині піднімає все, сайт відкривається на :3000 з даними.
- Ручний сценарій з розділу 8 спеки агента проходить.
- pytest на кожну дію підтримки (успіх + кожна помилка цілісності) і на CRUD-правила
  видалення; тести бекенду ганяються на окремій тестовій базі Postgres у Docker.
- Через MCP-клієнт `find_slots` + `reschedule_booking` змінюють бронювання, і зміна видна в
  адмінці з `by: agent`.
- Повідомлення в чаті підтримки доходить до заглушки агента і відповідь з'являється в чаті.

### 5.9 Документація

На кожну фічу — `docs/features/<фіча>/` з 10 файлами: FEATURE.md, business-context.md,
end-to-end-flow.md, entry-points.json, per-app-responsibility.md, backend-structure.md,
frontend-structure.md, data-model.md, integration-points.md, known-gotchas.md.
Фічі: `booking-api`, `mcp-server`, `support-chat`, `admin-panel`, `business-page`
(сторінка бізнесу + запис), `support-widget` (якщо встигнемо).

## 7. Відкриті питання до тіммейта

- Чи ок доповнення до контракту (`no_show_fee`, CRUD, чат).
